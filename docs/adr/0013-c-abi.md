# ADR 0013: Stable C ABI over nf-core

- Status: **Proposed**
- Date: 2026-09-27
- Deciders: owner (Marius Carlsson); proposed by the C ABI engineer (nfb-cabi)
- Source: `architecture/BLUEPRINT.md` §5 and §11; ADR 0007 (Rust core, "C++/Unity/Unreal via a C ABI"); `bindings/python/src/lib.rs` (the capability set to mirror); SEC-090/091 (`tools/hw-guard`). Company name: NeuroForge Bio.

## Context

ADR 0007 puts all shared SDK logic in `core/nf-core` and reaches C++, Unity (P/Invoke) and Unreal through a C ABI. Those three consumers are compiled with different compilers and runtimes and cannot see Rust types, Rust panics or Rust allocators. The ABI therefore has to be:

- plain C (no C++ in the interface, no Rust layout);
- versioned independently of the crate version, so that a binary built against one header keeps working with a newer library;
- impossible to crash through: a panic that unwinds into C is undefined behaviour;
- explicit about who owns every byte and which calls may run on which threads.

## Decision

A new crate `bindings/c` (`neuroforge-c`, library name `neuroforge`) builds a `cdylib` and a `staticlib` over nf-core with the `stream` feature. `cbindgen` generates `bindings/c/include/neuroforge.h`, which is checked in. A header-only C++17 wrapper lives in `bindings/cpp/include/neuroforge.hpp`. nf-core itself is not changed.

### Rules

1. **Naming.** Every symbol starts with `nf_` (functions, types) or `NF_` (constants). Names follow the hw-guard denylist (SEC-090).
2. **Status codes.** Every fallible function returns `nf_status` (`int32_t`); `NF_OK` is 0. Codes are `#define` constants, not a C enum, so that no caller can pass an out-of-range discriminant into Rust. New codes may be added in a minor version; callers must treat unknown non-zero codes as errors.
3. **Error text.** On failure, `nf_last_error()` returns a NUL-terminated UTF-8 message for the calling thread. Every call clears it on entry and again on success (CABI-T1), so a failing nested call inside a callback cannot leave stale text behind an `NF_OK`; callers read it only after a non-OK status. The pointer stays valid until the next `nf_` call on the same thread. `nf_last_error_detail()` carries a problem+json body for `NF_ERR_HTTP`.
4. **No panics across the boundary.** Every exported body runs inside `catch_unwind`. A caught panic returns `NF_ERR_PANIC` (functions without a status return a neutral value: `NULL`, 0 or `false`). Callbacks from C into Rust are C functions and cannot unwind.
5. **Strings in.** Short strings (paths, IDs, names) are NUL-terminated UTF-8 `const char*`. JSON documents and binary data are `(const uint8_t* ptr, size_t len)`; `ptr` may be `NULL` only when `len` is 0. Invalid UTF-8 returns `NF_ERR_INVALID_ARG`, it is never replaced.
6. **Memory out.** Variable-size results come back in two ways, both documented per function:
   - **Library-owned** `nf_buf { uint8_t* data; size_t len; }`, released with `nf_buf_free`. `data[len]` is always a NUL byte (not counted in `len`), so text results can be used as C strings. `nf_buf_free` on a zeroed or already-freed buffer is a no-op.
   - **Caller-allocated** buffers for bulk sample data (`nf_recording_read`): the caller passes `(out, capacity)`; `*out_len` receives the needed size, and `NF_ERR_BUFFER_TOO_SMALL` is returned when the buffer is too small or `NULL`, so a size query is one call with `out = NULL`.
7. **Handles.** Stateful objects are opaque pointers (`nf_recording*`, `nf_wal*`, ...) with one constructor that writes `*out` and one `nf_<type>_free`, which accepts `NULL`. A handle may only be freed once and not while another thread is using it.
8. **Thread safety** is stated per type in the header. Pure functions (hashing, IDs, verification) are thread-safe. Read-only handles (`nf_recording`, `nf_chunk`, `nf_device_key`) may be shared. Stateful handles lock internally; the one blocking call (`nf_sender_run`) is stopped from another thread with `nf_sender_stop`.
9. **Transports stay with the caller.** nf-core has no network stack of its own yet (the Python binding injects one). The C ABI takes a table of C callbacks for the ingest RPCs and for HTTP, plus a token callback; the retry, signing, batching and auth logic stays in Rust.
   - **Transport requirements (SEC-030, CABI-M1, ABI 1.2.1).** Every caller transport MUST:
     - use TLS 1.3 only (plain http only to loopback);
     - verify the certificate chain and hostname;
     - never follow redirects, and never send `authorization` to any other host;
     - enforce `timeout_s`;
     - never log, cache or persist auth values, headers or bodies.

     The requirements are stated on `nf_http_transport` and `nf_ingest_transport` in the header, and a header test checks that they are there.
   - The library caps what a callback may hand back:
     - an HTTP response (header names and values plus body) at `NF_MAX_RESPONSE_BYTES` (64 MiB, fixed). A transport that wants less, such as the engine defaults at 16 MiB, enforces it itself. A per-client setter is on the owner-held 1.3 list;
     - response headers at `NF_MAX_RESPONSE_HEADERS` (256) and `NF_MAX_RESPONSE_HEADER_BYTES` (256 KiB);
     - ingest replies and tokens at `NF_MAX_REPLY_BYTES` (1 MiB).

     Exceeding a cap fails the call whatever the callback returns.
   - The library's own error texts never contain the auth value; tests check this. Caller callback messages are passed through as given.
   - The engine SDKs' default transports and their conformance suite (docs/hive/CABI-M1-PLAN.md) close CABI-M1.
10. **Versioning.** `NF_ABI_VERSION_MAJOR/MINOR/PATCH` are in the header, and `nf_abi_version()` returns `major << 16 | minor << 8 | patch` of the loaded library. A caller is compatible when the majors match and the library minor is at least the header minor. Adding functions or status codes is a minor change. Changing a signature, struct layout or meaning is a major change; the previous major is kept in the same library for at least one release when possible. `nf_core_version()` reports the nf-core crate version separately.
11. **Header drift.** `node bindings/c/tools/header.mjs --check` regenerates the header with cbindgen and fails on any difference, and a cargo test checks that every exported symbol is declared in the checked-in header.
12. **Hostile input is an error, never UB (ABI 1.2, nfb-security CABI-L1..L5).**
    - Every caller pointer is checked for alignment, and every `(ptr, len)` for a byte size within `isize::MAX`, before it is dereferenced. A violation is `NF_ERR_INVALID_ARG`, and the void free functions ignore such a pointer.
    - Recording metadata is untrusted: sizes use checked arithmetic, at most 65,536 channels are accepted at open (`NF_ERR_CORRUPT` above that), and one read may touch at most 1 GiB of stored data (`NF_ERR_INVALID_ARG`, "split the range").
    - A WAL needs an explicit key source. `nf_wal_open` with neither `key32` nor `dpapi_key_path` is `NF_ERR_INVALID_ARG`; the in-memory key is only available through `nf_wal_open_ephemeral`.
    - This tightened the 1.1 behaviour of `nf_wal_open`. That was accepted as a minor change because 1.x had not been released or merged, and its only consumer (nfb-engine) was told.
    - DPAPI sealing without entropy (NR-L6) and each callback table's thread contract are stated in the header.

### What the ABI exposes (1.0)

- version and info, status names, last error, `nf_buf_free`;
- hashing spec v1: canonical JSON, number formatting, blob/pipeline-version/chunk/prov-batch IDs, chain verification, ID validation, dtypes;
- hashing spec v2: audit batches and chains, provenance node hashes, consent records and chains, ruleset hashes, sweep labels, training-subject hashes, training manifests, chunk timing hashes, and Ed25519 verification of stream chunks, device tokens, prov-batch signatures, anchors and deletion certificates;
- local data, read-only: `nf-signal/1` recordings (metadata, channels, samples, timestamps) and the content-addressed chunk cache (hash-verified reads). ABI 1.1 adds `nf_recording_read_f64`, which returns physical values (`stored * scale + offset`) as doubles for the engine SDKs;
- the offline provenance recorder;
- streaming: device keys (generate, import seed, DPAPI-sealed on Windows, device tokens), the encrypted WAL, the stream writer (push, clock samples, flush) and the sender (run, stop, state, finish, stats) over caller transports;
- the API client (auth tokens, retries, problem+json) over a caller HTTP transport, and the SEC-030 base-URL check.

### Not exposed, on purpose

- **Anything that sends data or instructions to acquisition or stimulation hardware.** Data flows device to SDK to platform only (SEC-090/091). `tools/hw-guard` scans `bindings/`.
- Writing recordings or cache entries (`zarr::write_signal`, `ChunkCache::put`): local data is read-only through this ABI until a consumer needs it.
- Raw signing with a device key and exporting key material. Keys only sign chunks and tokens inside the writer and sender.
- Raw WAL record access (`read`, `ack`, `pending`), which is sender-internal.
- Payload and preimage builders of the hashing spec. The IDs, hashes and verifications cover the consumers' needs; the builders stay testable in nf-core.
- Signal processing (BLUEPRINT §5: stays in Python/MNE).

## Consequences

- C++, Unity and Unreal get one binary and one header; the C++ wrapper adds RAII and exceptions on top, with no logic of its own.
- Every capability added to nf-core needs a deliberate ABI addition; nothing leaks through automatically.
- Callback transports mean the engine SDKs bring their own HTTP/gRPC stack (UnityWebRequest, Unreal HTTP), which is what those engines expect.
- CI needs `cbindgen` for the header check.
