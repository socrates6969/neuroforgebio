# Cryptography inventory (CBOM-style), platform M2

Status: **draft for review** (SEC-038 asks for review at every milestone). Written from the code on branch
`feature/m2-ingest` (2026-09-26); every row names the file that implements it, so the table can be checked
against the code. Format follows the CycloneDX CBOM idea (asset → algorithm → key → where used → lifecycle),
kept as Markdown until the SBOM tooling (`tools/sbom-props`) emits a machine-readable CBOM.

All primitives come from vetted libraries (`cryptography` 50.0.1, Python `hashlib`/`hmac`/`secrets`, PyJWT
2.15.0, AWS KMS, Windows DPAPI). No custom primitives (SEC-032).

## 2. Where keys and secrets live

| Secret | At rest | In memory | Never |
|---|---|---|---|
| Tenant KEK | AWS KMS (deployments); nowhere (dev `LocalKms`, lost on restart) | `LocalKms` only | exported, logged, in `repr` |
| Subject DEK | wrapped in `subject_key` (Postgres, RLS) | plaintext cache in `Keyring` (dropped on shred) | logged (log-scan test, SEC-147) |
| API-key pepper | KMS-encrypted secret (deployments) | `SecretProvider` | in the DB next to hashes |
| API-key secret | only its HMAC | request lifetime | stored, logged, audited (audit payload scan) |
| Device private key | the device (DPAPI/Keychain/libsecret in nf-core 4.2) | edge process | sent to the platform |
| WAL key | DPAPI-sealed file next to the WAL (Windows) | edge process | on disk in plaintext |
| Provenance signing key (Ed25519) | KMS (deployments, not built); env seed `NF_PROV_SIGNING_KEY` (dev) | `provenance.signing` keyring | logged, stored in the DB, exported (only public keys are configured for verification) |

## 3. Open items (for the milestone review)

- DB backups still contain wrapped DEKs until they expire (crypto-shred completeness, D4).
- The M2-M5 tags (`auditb`, `nf.device-token.v1`, `nf.stream-chunk.v1`, `nf.prov-node.v1`, `nf.consent-record.v1`,
  `nf.ruleset.v1`, `nf.sweep-variant.v1`, `nf.wal.v1`), the M6 tags (`nf.training-subject.v1`,
  `nf.training-manifest.v1`) and the signed documents (`nf.prov-anchor/v1`,
  `nf.consent-anchor/v1`, `nf.deletion-certificate/v1`, provenance batch signatures) are registered in hashing
  spec v2 (`docs/spec/hashing.md` §8-§11, vectors `spec/test-vectors/ids-v2.json`). Still open: nf-core (Rust) does
  not check `ids-v2.json` yet, and the batch/anchor/certificate signatures carry no domain tag (spec §11 item 1).
- Asymmetric algorithms in use (Ed25519, RS256/PS256/ES256 via the IdP, TLS key exchange) are not
  post-quantum; migration path: versioned token prefix (`nfd2` with ML-DSA), IdP support, hybrid ML-KEM at the edge.
- Edge WAL key storage outside Windows (Keychain, libsecret) and device-key storage in the OS keystore: nf-core 4.2.
- mTLS per-device client certificates (enterprise option of SEC-016): not built.
