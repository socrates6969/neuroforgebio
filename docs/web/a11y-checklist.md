# A11y checklist for new or changed pages

Built from bug classes actually found on this site (docs/hive/A11Y-AUDIT.md and the T4/T6/gallery
findings), not a generic list. Each item: the check, and the file/test that enforces it today.
Rows 2-5 and 7 now have an automated check (`apps/web/test/a11y-checklist.test.mjs` +
`apps/web/test/a11y-checklist-lib.mjs`, static heuristics over built HTML/CSS and page source, both
themes, every inner page — the homepage is not checked). None of them catch every case; each
catches the shape of bug the audit already found, plus the common variants. **"Review by eye" is
narrowed by these, not retired** — the "Enforced by" column says exactly what's still manual. Row 1
was already covered (`theme-tokens.test.mjs`/`style-lint.test.mjs`); row 6 needs human judgement and
has no test.

A rare, reviewed false positive from rows 2-5/7 goes in `A11Y_EXCEPTIONS` in
`apps/web/test/a11y-checklist.test.mjs` — keyed by row + route + selector, with a one-line reason.
The list starts empty, and an entry that no longer matches a real finding fails the test (so it
can't silently outlive the bug it was excusing).

| # | Check | Found as | Enforced by |
|---|---|---|---|
| 1 | Every `var(--x)` you add resolves to a real token defined in **both** `packages/themes/clinical/tokens.css` and `.../cosmos/tokens.css` — not just a hardcoded fallback in the `var()` call itself. A fallback for a token that doesn't exist always applies, silently, in every theme. | `BuildStatePill.astro` referenced `--color-success`/`--color-success-light` (neither theme defines them); its fallback colours measured ~2.5:1, under the 4.5:1 AA minimum, identically in both themes. | `packages/ui/test/style-lint.test.mjs` (packages/ui + packages/figures) **and** `apps/web/test/theme-tokens.test.mjs` (everything under `apps/web/src`) — together, every first-party source is covered. A `var(--x, fallback)` is only allowed when `--x` itself is a real token in both themes, or the fallback resolves through a nested `var(--y)` to one that is. |
| 2 | If a page wraps its own sections in `display: grid` or `display: flex`, add `min-width: 0` on the items unless you've checked every descendant wraps or truncates. Grid/flex items default to `min-width: auto` (their content's min-content width), so one unbreakable-width descendant (a long code line, an unbroken hash) can force the whole grid — and the page — wider than the viewport, even if that descendant has its own `overflow-x: auto`. | `gallery.astro`'s `.blocks { display: grid }` let `PipelineSteps`' code-sample lines force a real 7px horizontal-scroll overflow at 360px, cosmos only (font-metric difference tipped a near-miss into a real failure). | `apps/web/test/a11y-checklist.test.mjs` (static, every inner page, both themes) flags a component-scoped or page-only grid/flex container when **both** hold: (a) an item has no escape — every grid column track has a fixed minimum (e.g. `minmax(0,1fr)` or `220px`), a rule matching the item sets `min-width: 0`, or the item itself scrolls; (b) that item holds something of unbreakable width — a `<pre>`, an `overflow-x: auto/scroll` box, or a run of 40+ characters with no break opportunity (a hash, a URL, or `white-space: nowrap` text). Judged per container **instance**, so a fixed twin with the same class can't mask a broken one. No layout engine: every media query counts as applying, cascade order is ignored, and a rule from the shared site-wide bundle (packages/themes, `nf-*` utilities) isn't a container here — only page-local/component-scoped rules are. `apps/web/e2e/visual.spec.ts` (`scrollWidth - clientWidth <= 0` at 360/768/1440px, CI-only) is still the real overflow check. |
| 3 | Don't mark a region `aria-live` if its content updates continuously or on every interaction (a live scoreboard, a panel that re-renders in full on each run). Screen readers announce every change; a region that updates often, or updates in full when a summary already announced the gist, creates noise instead of information. | `/arena`'s visible results card (`aria-live="polite"`, re-rendered via `innerHTML` on every run) sits alongside its own dedicated hidden status line — both fire on the same event. | `apps/web/test/a11y-checklist.test.mjs` flags two cases: (a) a visible live region (not `.nf-visually-hidden`) whose rendered markup holds a list, table, heading or 2+ paragraphs; (b) a page script that writes `innerHTML`/`insertAdjacentHTML` into a live region it looks up by a `data-*` hook or id. `aria-live="off"` is never flagged. Doesn't catch a region that's empty at render and filled later by a helper function — still review the diff for `aria-live`. |
| 4 | One `aria-live` region per logical event, and it should be the **hidden**, purpose-built status line — not also the visible panel showing the result. If you already have a `<p class="nf-visually-hidden" aria-live="polite">`, nothing else nearby should also be `aria-live`. | Same `/arena` finding as #3: the visible `.arena-card` was *also* `aria-live="polite"`, alongside the hidden status paragraph that already announces the short version. `/playground` gets this right — only its hidden status line is live. | `apps/web/test/a11y-checklist.test.mjs` flags a visible live region paired with a hidden one when the page script updates both from the same handler (a listener callback or a method, followed one call level); if the script can't be resolved, falls back to structure — flagged when both sit in the same section/article/form/fieldset or `data-*` component root. Live regions with different purposes (an error summary and a separate "saved" confirmation) pass. One handler writing both in if/else branches is still flagged — that case needs an `A11Y_EXCEPTIONS` entry with a reason. |
| 5 | Any content reachable **only** via a `title=` attribute is reachable by mouse-hover users only — not keyboard, not touch, and inconsistently by screen readers. If it's worth saying, say it as visible text (or `.nf-visually-hidden` text) instead. | `/law-tracker`'s statutory-definition `title=` and `/docs/api`'s response-description `title=` — both fixed by moving the text into the DOM (visible or `.nf-visually-hidden`) instead of an attribute. | `apps/web/test/a11y-checklist.test.mjs` flags a `title=` only when all hold: no `aria-label`/`aria-labelledby`; for img/input, the alt or label doesn't contain the title text; the element's own text doesn't contain it; and the text appears nowhere else on the page (visible or `.nf-visually-hidden`). `iframe` titles are allowed. Catches the common case, not every case: matching is case-insensitive substring, so a short/common title ("Info", "Details") that happens to appear elsewhere gives a false negative — still review short titles by eye. |
| 6 | New user-facing text goes through the content system (`packages/content` for shared/i18n'd copy, or the page's own local content JSON like `apps/web/src/docs/index.json`) — never a string literal in a `.astro` template. This is what makes translation possible later and keeps one source of truth. | `BuildStatePill.astro` hardcoded `"Built, tested internally"` in the template, ignoring the `ui.buildStateLabels` field that already had an EN+NO translation ready. Only reachable from English-only pages today, so it wasn't yet visibly wrong — but it was a ticking i18n bug. | Partially: `packages/content/test/content.test.mjs`'s i18n key-parity test (`ui.no.json` keys must match `ui.en.json`) catches **drift once text is in content**, but can't catch a string that bypassed content entirely. Review by eye for string literals in JSX-like template expressions. |
| 7 | Every `<input type="range">` (or other widget whose visible value differs from its native accessible value) needs a dynamic `aria-valuetext` kept in sync with whatever the sighted user sees, not just the raw index/step number. Set it once at render **and** update it in the same handler that updates the visible `<output>`. | `/arena`'s neurons range had no `aria-valuetext` at all — a screen-reader user would hear the raw slider index, not the actual neuron count shown next to it. `/playground`'s equivalent slider gets this right: `this.ui.neurons.setAttribute('aria-valuetext', ...)` on every change (`apps/web/src/scripts/playground.ts`). | `apps/web/test/a11y-checklist.test.mjs` checks a range only when it has a companion visible value display (an `<output for>`, an `aria-describedby`/`aria-controls` target, an `<output>` in the same `<label>`, or a nearby element its own input/change handler writes into). Such a range must carry `aria-valuetext` at render (unless inside a `hidden` subtree at render), and the same handler must update `aria-valuetext` along with the visible value (followed one call level). A bare range with no readout passes. |

## Using this

- New page or component: skim the "Check" column before opening a PR.
- Changed a shared component that other pages also render: #1 and #2 matter most, since a small
  CSS change can surface on pages you didn't test.
- Nothing here replaces `apps/web/test/html.test.mjs` (ids, ARIA refs, one h1/main, alt text) or
  `apps/web/e2e/a11y.spec.ts` (axe, CI-only) — this list is for the bug classes those two don't
  catch. `apps/web/e2e/visual.spec.ts` (real layout, CI-only) stays the ground truth for row 2;
  none of rows 2-5/7's checks run a browser or execute JS.
- A finding from rows 2-5/7 that's a real, reviewed false positive gets an `A11Y_EXCEPTIONS` entry
  in `apps/web/test/a11y-checklist.test.mjs` (row + route + selector + a one-line reason) — never a
  silent skip. Don't add one to make a real finding go away; report it instead.
- Add a row here whenever a real (not theoretical) a11y bug is found and fixed; drop the "Enforced
  by" column to "None" honestly rather than implying a check exists when it doesn't.
